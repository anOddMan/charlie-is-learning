总览 Overview

Claude Code 的工具集是构建在 Anthropic API tool-use 原语之上的封闭式工具箱。 每个工具经过精心的安全沙箱封装，通过权限分级（只读 / 需审批 / 危险操作）确保用户可以完全控制 Agent 的行为边界。 工具之间遵循高内聚低耦合原则：每个工具只做一件事，并通过组合而非膨胀来应对复杂场景。

一、文件系统 6 tools

代码 Agent 的感知层。所有代码理解、修改、搜索的入口。专用工具替代 UNIX 命令（Read 替代 cat、Grep 替代 rg、Glob 替代 find），统一权限管控。

Read 只读高频
用途
读取本地文件内容。支持文本、图片（多模态视觉）、PDF、Jupyter Notebook (.ipynb) 等格式。
原理
直接读取文件系统，通过文件扩展名判断类型。图片和 PDF 使用多模态能力直接理解内容。大文件支持 offset/limit 分段读取。PDF 大文件需 pages 参数按页码范围读取（上限 20 页/次）。
建设理由
Agent 必须能"看到"代码才能工作。不提供目录列表（该职责属于 Glob），只做文件内容读取。与 Write/Edit 有明确的职责边界。
应用实例
JSON-RPCTool Call
// 1. 读取完整文件（默认前 2000 行）
{ "file_path": "/abs/path/to/src/App.tsx" }

// 2. 分页读取大文件
{ "file_path": "/abs/path/to/large.log", "offset": 1000, "limit": 500 }

// 3. 读取 PDF 指定页码范围
{ "file_path": "/abs/path/to/paper.pdf", "pages": "1-5" }

// 4. 读取图片（多模态，无需额外参数）
{ "file_path": "/abs/path/to/screenshot.png" }
Write 需审批写操作
用途
创建新文件或整体覆写已有文件。必须先用 Read 读取过目标文件才能覆写。
原理
全量内容替换。对已有文件要求先 Read（防止误覆写未读文件）。新建文件无此限制。文件路径必须是绝对路径。
建设理由
与 Edit 分工明确：Write 用于新建/全量替换，Edit 用于增量修改。Write 不显示 diff，适合初始创建或确定要整体重写的场景。
应用实例
JSON-RPCTool Call
// 1. 创建新文件（无需先 Read）
{
  "file_path": "/abs/path/to/src/utils/helpers.ts",
  "content": "export function greet(name: string): string {\n  return `Hello, ${name}`;\n}\n"
}

// 2. 覆写已有文件（必须先 Read 过）
{
  "file_path": "/abs/path/to/src/App.tsx",
  "content": "import React from 'react';\n// ... full new content\n"
}
Edit 需审批高频主力
用途
精确字符串替换（diff 式编辑）。日常代码修改的主力工具。
原理
在文件中查找 old_string → 替换为 new_string。old_string 必须在文件中唯一（否则报错），可通过提供更多上下文使其唯一。支持 replace_all 参数进行全量替换。
建设理由
避免每次修改都发送整个文件内容，大幅减少 token 消耗。相比 sed/awk 更安全可靠（精确匹配，不会误伤）。diff 式编辑也比全量覆写更容易做 Code Review。
应用实例
JSON-RPCTool Call
// 1. 精确替换单处
{
  "file_path": "/abs/path/to/src/utils.ts",
  "old_string": "function add(a: number, b: number): number {\n  return a + b;\n}",
  "new_string": "function add(a: number, b: number): number {\n  // 增加溢出检查\n  return a + b;\n}"
}

// 2. 全量重命名变量
{
  "file_path": "/abs/path/to/src/UserProfile.tsx",
  "old_string": "userName",
  "new_string": "displayName",
  "replace_all": true
}
Glob 只读文件发现
用途
文件名通配符匹配，按修改时间排序返回匹配文件列表。
原理
基于文件系统的 glob 模式匹配，支持 `**` 递归匹配。比 `ls`/`find` 更快，且权限更安全。
建设理由
Shell 的 `ls` 和 `find` 需要权限审批且输出格式不可控。专用 Glob 工具提供统一的文件发现接口，输出结构化路径列表。
应用实例
JSON-RPCTool Call
// 1. 查找所有 TypeScript 组件
{ "pattern": "src/components/**/*.tsx", "path": "/abs/path/to/project" }

// 2. 查找所有 Markdown 文档
{ "pattern": "docs/**/*.md" }

// 3. 查找所有配置文件
{ "pattern": "*.{json,yaml,yml,toml}" }
Grep 只读高频
用途
文件内容正则搜索。支持正则、文件类型过滤、上下文行、多行模式。底层基于 ripgrep。
原理
使用 ripgrep 引擎执行正则匹配。output_mode 支持三种模式：content（匹配行 + 上下文）、files_with_matches（仅文件路径）、count（匹配计数）。支持 glob 文件过滤和 type 类型过滤。
建设理由
代码搜索是最高频操作之一。专用工具比 Shell grep/rg 更快、更安全、输出更结构化。多行模式支持跨行搜索（如搜索函数签名跨越换行）。head_limit 和 offset 支持结果分页。
应用实例
JSON-RPCTool Call
// 1. 搜索函数定义（含上下文）
{
  "pattern": "function\\s+handleLogin",
  "output_mode": "content",
  "-C": 3,
  "glob": "*.ts"
}

// 2. 查找所有调用特定 API 的文件
{
  "pattern": "fetch\\(.*/api/users",
  "output_mode": "files_with_matches"
}

// 3. 跨行搜索 React 组件
{
  "pattern": "export\\s+default\\s+function\\s+\\w+\\s*\\([^)]*\\)\\s*\\{",
  "type": "tsx",
  "multiline": true
}
LSP 只读语义分析
用途
Language Server Protocol 代码智能：跳转定义、查找引用、悬停类型信息、调用层次分析。
原理
连接项目已配置的 LSP 服务器（TypeScript、Python、Rust 等），通过标准 LSP 协议请求语义信息。所有操作需要 filePath + line + character 定位符号位置。
建设理由
语义级代码理解比文本搜索更准确。文本搜索 "getUser" 可能匹配注释、字符串、变量名的一部分；LSP 能精确定位到函数定义、区分同名不同模块的符号。利用 IDE 已有的语言分析基础设施。
应用实例
JSON-RPCTool Call
// 1. 跳转到函数定义
{ "operation": "goToDefinition", "filePath": "src/App.tsx", "line": 42, "character": 10 }

// 2. 查找所有引用（谁调用了这个函数）
{ "operation": "findReferences", "filePath": "src/api.ts", "line": 88, "character": 5 }

// 3. 分析调用层次（谁调了谁）
{ "operation": "incomingCalls", "filePath": "src/utils.ts", "line": 15, "character": 1 }

// 4. 查看类型信息（Hover）
{ "operation": "hover", "filePath": "src/types.ts", "line": 12, "character": 18 }

二、Shell 执行 2 tools

与操作系统交互的桥梁。双轨制设计（Bash + PowerShell）覆盖 macOS/Linux 和 Windows 生态。支持后台运行、超时控制、工作目录持久化。

Bash 需审批Shell
用途
执行 Bash/POSIX shell 命令。工作目录跨调用持久化，但 Shell 状态（变量、函数）不保留。
原理
在用户 Shell 环境中执行命令（从 profile 初始化）。支持超时控制（默认 120s，最大 600s）。run_in_background 模式用于长时间任务。
建设理由
运行构建、测试、git、包管理器等 CLI 操作是编码 Agent 的刚需。不建议用于文件搜索/读取/编辑（有专用工具更快更安全）。
应用实例
JSON-RPCTool Call
// 1. 运行测试套件（超时 5 分钟）
{
  "command": "npm test -- --coverage",
  "description": "Run test suite with coverage",
  "timeout": 300000
}

// 2. 后台启动开发服务器
{
  "command": "npm run dev",
  "description": "Start dev server",
  "run_in_background": true
}

// 3. Git 操作（查看最近提交）
{
  "command": "git log --oneline -10",
  "description": "Show recent git commits"
}
PowerShell 需审批ShellWindows
用途
Windows PowerShell 5.1 命令执行。与 Bash 平行选择，覆盖 Windows 原生操作。
原理
在 powershell.exe 中执行命令。不支持 `&&`/`||` 链式操作（用 `; if ($?) {}` 替代）、不支持三元/空合并运算符。文件编码默认 UTF-16 LE。
建设理由
Windows 用户原生体验；部分 Windows 专有操作（注册表、证书、COM 对象）只能用 PowerShell。双轨制确保跨平台覆盖无死角。
应用实例
JSON-RPCTool Call
// 1. 列出目录
{
  "command": "Get-ChildItem D:\\projects -Name",
  "description": "List project directory"
}

// 2. 检查环境变量
{
  "command": "$env:NODE_ENV",
  "description": "Check Node environment"
}

// 3. 条件执行（无 && 运算符）
{
  "command": "npm run build; if ($?) { npm run deploy }",
  "description": "Build and deploy on success"
}

三、任务管理 6 tools

内存中的结构化任务追踪系统。支持状态流转（pending → in_progress → completed）、依赖关系（blocks/blockedBy）、元数据。比自由文本的任务列表更可靠，自动反映进度。

TaskCreate / TaskGet / TaskList / TaskUpdate / TaskOutput / TaskStop 管理编排
用途
创建、查询、更新、停止结构化任务，建立任务间依赖关系。
原理
内存中的任务图（DAG）。每个任务有 id / subject / description / status / owner / blocks / blockedBy。状态严格单向流转：pending → in_progress → completed（或 deleted）。后台任务（Bash/Agent）与 TaskOutput 联动。
建设理由
复杂多步骤任务需要可靠的追踪机制。依赖图确保不会跳过前置步骤。用户通过 TaskList 快速了解全局进度。
应用实例
JSON-RPCTool Call 序列
// Step 1: 创建三个任务
{ "subject": "设计数据库 Schema", "description": "用户表 + 订单表 + 索引设计" }  // → id: "1"
{ "subject": "实现 API 端点", "description": "CRUD for /api/users, /api/orders" }   // → id: "2"
{ "subject": "编写集成测试", "description": "supertest + in-memory DB" }    // → id: "3"

// Step 2: 设置依赖（测试依赖 API，API 依赖 Schema）
{ "taskId": "2", "addBlockedBy": ["1"] }          // API 等待 Schema
{ "taskId": "3", "addBlockedBy": ["2"] }          // 测试等待 API

// Step 3: 开始工作，逐个完成
{ "taskId": "1", "status": "in_progress" }  // 开始 Schema
{ "taskId": "1", "status": "completed" }     // Schema 完成 → API 自动解封

// Step 4: 查看进度
{}  // TaskList → [{id:"1", status:"completed"}, {id:"2", status:"pending"}, {id:"3", status:"pending", blockedBy:["2"]}]

四、子代理调度 1 tool, 多类型

子代理是 Claude Code 实现上下文隔离和并行化的核心机制。每个子代理拥有独立的工具集和上下文窗口，支持多种专业化类型。

Agent 需审批核心并行
用途
启动子代理（Sub-agent）处理复杂、多步骤或可并行的任务。
原理
创建独立 Agent 实例：独立的上下文窗口 → 独立的工具调用循环 → 返回结构化结果。类型系统决定工具集和 prompt：Explore（只读搜索）、Plan（架构设计）、code-reviewer（审查）、general-purpose（通用）。isolation: "worktree" 在 Git 临时分支上工作。
建设理由
上下文隔离：搜索结果不污染主会话；并行化：多个子代理并发执行独立任务；专业化：不同类型有优化的工具集和 prompt。
⚠️ 注意：这是 Claude Code 内置的子代理机制，与 Anthropic 发布的 Claude Agent SDK 是两套独立的实现。
应用实例
JSON-RPCTool Call
// 1. 启动只读探索子代理（搜索代码库）
{
  "description": "Find auth middleware",
  "subagent_type": "Explore",
  "prompt": "Find all authentication middleware files and report their patterns."
}

// 2. 启动架构规划子代理
{
  "description": "Design caching strategy",
  "subagent_type": "Plan",
  "prompt": "Design a caching layer with TTL, invalidation strategy, and fallback."
}

// 3. 并行执行多个独立任务（同一消息中多个 Agent 调用）
// Agent 1: Lint 检查
{ "description": "Run linter", "prompt": "Run eslint and report errors." }
// Agent 2: 类型检查（与 Agent 1 并行）
{ "description": "Type check", "prompt": "Run tsc --noEmit and report errors." }
// Agent 3: 测试（与 Agent 1、2 并行）
{ "description": "Run tests", "prompt": "Run full test suite and report failures.", "run_in_background": true }

// 4. Worktree 隔离子代理（在临时分支上实验）
{
  "description": "Experiment with new auth",
  "subagent_type": "general-purpose",
  "isolation": "worktree",
  "prompt": "Replace JWT auth with session-based auth. Commit the changes."
}

五、计划模式 2 tools

Plan → Approve → Execute 三步法的技术保障。进入计划模式后只能探索不能编辑，必须通过审批才能进入实现阶段。

EnterPlanMode / ExitPlanMode 流程架构
用途
EnterPlanMode 进入只读探索状态设计方案；ExitPlanMode 提交方案等待用户审批。
原理
切换会话到 plan 模式：可读取/搜索但不能编辑文件。方案通过 ExitPlanMode 从计划文件读取并展示给用户。用户审批通过后退出计划模式，进入执行阶段。
建设理由
防止"先动手再思考"——复杂任务需要先规划再编码。用户审批节点确保 Agent 的方案与用户期望对齐，避免浪费精力。
应用实例
交互流程Plan Mode Lifecycle
// 用户: "实现用户登录功能"
// ↓ Claude Code 判断这是多方案多文件任务 ↓

{ "tool": "EnterPlanMode" }
  // → 进入计划模式
  // → 探索现有代码: Read + Grep + Glob
  // → 设计方案: JWT vs Session, 中间件位置, 错误处理策略
  // → 撰写计划文件: plan.md

{ "tool": "ExitPlanMode" }
  // → 用户看到方案: "使用 JWT + 中间件 + HttpOnly Cookie"
  // → 用户审批通过

// → 退出计划模式，开始 Edit + Write 实现代码

六、用户交互 2 tools

保持"人在环中"的决策权。结构化问答在关键节点让用户选择，推送通知在异步任务完成时提醒用户。

AskUserQuestion / PushNotification 交互
用途
AskUserQuestion：结构化问答（单选/多选 + 预览），用于澄清需求和选择方案。PushNotification：桌面/手机通知，用于异步任务完成提醒。
原理
AskUserQuestion 渲染带选项的 UI 组件，支持每个选项的预览内容（代码片段、ASCII 图等）。PushNotification 通过终端通知机制 + Remote Control 推送到手机。
建设理由
AI 不能替用户做价值判断。歧义必须澄清，关键决策必须有审批节点。异步完成的通知让用户不必守在终端前。
应用实例
JSON-RPCTool Call
// 1. 结构化单选（含预览）
{
  "questions": [{
    "question": "认证方案选择哪个？",
    "header": "Auth 方案",
    "multiSelect": false,
    "options": [
      { "label": "JWT (推荐)", "description": "无状态，适合微服务，但需要处理刷新逻辑" },
      { "label": "Session",  "description": "传统方案，服务端有状态，Redis 存储" },
      { "label": "OAuth 2.0", "description": "第三方登录，但需要额外配置" }
    ]
  }]
}

// 2. 异步完成通知
{
  "message": "构建完成：3 passed, 0 failed (12.4s)",
  "status": "proactive"
}

Cron 表达式驱动的定时任务。支持单次提醒和周期性检查，仅存在于当前会话内存中。

CronCreate / CronDelete / CronList 调度
用途
创建、删除、列出基于 Cron 表达式的定时任务。
应用实例
JSON-RPCTool Call

// 下午 3 点一次性提醒
{ "cron": "57 14 27 5 *", "prompt": "提醒用户检查部署状态", "recurring": false }

九、循环控制 1 tool

/loop 自主循环模式下的自适应唤醒机制，根据任务类型智能选择等待间隔。

ScheduleWakeup 循环
用途
在 /loop 动态模式下，根据任务类型和预期耗时调度下次唤醒时间（60s~3600s）。
原理
以 Anthropic prompt cache 的 5 分钟 TTL 为分界：<270s 保持缓存热度；>300s 接受缓存失效但换取更长等待。1200s+ 是默认的空闲心跳间隔。

十一、技能系统 1 tool

设计原则 8 Principles

指导工具集设计和演进的核心理念。

1. 专用优于通用

Read/Grep/Glob 替代 cat/grep/find。每个工具只做一件事，通过组合应对复杂场景。专用工具提供更结构化的输出、更精确的权限控制。

2. 安全优先

三级权限体系：只读（自动放行）、需审批（Edit/Write/Bash）、危险操作（rm -rf / force push 必须确认）。沙箱执行 + hooks 拦截。

3. Token 效率

Edit（diff）替代 Write（全量）减少上下文消耗。Agent 子代理隔离搜索结果，不污染主会话。Prompt cache 5 分钟 TTL 指导调度策略。

4. 结构化优先

NotebookEdit 而非 sed 操作 JSON。Task* 系统而非自由文本追踪。信息输出统一结构化，便于程序化消费。

5. 可扩展性

MCP 协议（浏览器工具由 Playwright MCP 插件提供）和 Skill 系统允许第三方扩展工具集，不修改核心代码。

6. 跨平台

Bash + PowerShell 双轨制，确保 macOS/Linux 和 Windows 都有一流体验。Windows 专有操作（注册表、证书）通过 PowerShell 覆盖。

7. 人在环中

AskUserQuestion（决策节点）、PlanMode（方案审批）、PushNotification（异步通知）。AI 不能替用户做价值判断，关键决策必须有审批。

8. 上下文隔离

Agent 子代理拥有独立上下文窗口。Worktree 在 Git 层面隔离文件系统。避免搜索噪音和实验性改动污染主工作流。

与 Claude Agent SDK 的对比 Differentiation

Claude Code 工具集 与 Claude Agent SDK 都构建在 Anthropic API tool-use 原语之上，但定位完全不同。

维度Claude Code 工具集Claude Agent SDK
性质 CLI 应用内的固定工具集 npm SDK 包，供开发者在自己的 App 中使用
实现者 Anthropic 团队（Claude Code 产品组） SDK 使用者自己实现工具逻辑
运行环境 Claude Code 沙箱（CLI 进程内） 开发者的 Node.js 进程
权限控制 Claude Code 三级权限 + hooks 开发者通过 canUseTool 回调自定义
可定制性 固定工具集，不可增删 完全掌控：可删减、增强、替换任意工具
扩展方式 MCP 插件 + Skill 系统 直接编写 TypeScript 代码定义工具
适用场景 终端用户交互式编码 程序化构建自定义 AI Agent
典型用例 "帮我重构这个模块" "在 CI 流水线中自动修复 lint 错误"
关键认知

两者工具集的"重复"是有意设计，不是冗余。 就像 macOS Terminal.app 和 iTerm2 都能 ls、cd、cat， 它们解决的是同一类问题（文件操作），但是两个独立的、互不依赖的产品。 Claude Code 的 Agent 工具（子代理调度）与 Claude Agent SDK 也完全无关——前者是内置的子代理机制，后者是面向开发者的 npm 包。
