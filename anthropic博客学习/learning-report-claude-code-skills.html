构建 Claude Code 的经验：Anthropic 如何运用 Skills 体系

来源：Anthropic 官方博客  |  作者：Thariq Shihipar  |  发布日期：2026-06-03  |  报告生成：2026-06-05

一句话总结：Skill 是一个文件夹（而非单个 Markdown 文件），内含指令、脚本、资源、配置等，AI Agent 可自动发现并按需加载。Anthropic 内部已积累数百个 Skill，覆盖从代码生成到运维的全流程。

九大技能类别

Anthropic 将内部使用的 Skill 归纳为 9 个类别：

#类别用途典型示例
1 库与 API 参考 教 Claude 正确使用内部/外部库 billing-lib、internal-platform-cli
2 产品验证 测试和验证代码是否正常工作（常结合 Playwright、tmux） signup-flow-driver、checkout-verifier
3 数据获取与分析 连接数据和监控栈 funnel-query、cohort-compare、grafana
4 业务流程自动化 自动化重复性工作流 standup-post、weekly-recap
5 代码脚手架 / 模板 为特定框架生成样板代码 new-<framework>-workflow、create-app
6 代码质量与审查 执行代码质量标准 adversarial-review、code-style
7 CI/CD 与部署 拉取、推送、部署代码 babysit-pr、deploy-<service>
8 Runbook（操作手册） 症状 → 多工具调查 → 结构化报告 <service>-debugging、oncall-runner
9 基础设施运维 带护栏的日常维护操作 <resource>-orphans、cost-investigation
关键洞察：这并不是一个"完整"的清单——Anthropic 团队强调这 9 个类别只是他们目前观察到的最有用方向。Skill 的最佳实践仍在快速演进中。

七条最佳实践

1. 不说显而易见的东西

Claude 已经知道如何编程。Skill 的价值在于提供将 Claude 推离常规思维路径的信息——即团队专属知识，而非通用的编码建议。

反例："写干净的代码，遵循语言惯例"——这对 Claude 是废话。
正例："这个项目用 FooService 而非 BarService 处理支付，因为我们 X 月迁移了"——这是 Claude 不知道的团队上下文。

2. 构建 "Gotchas"（陷阱/常见坑） 板块

这是整个 Skill 中信号密度最高的内容。记录 Claude 经常踩到的坑，随着新边界情况的发现持续更新。

"subscriptions 表是只追加（append-only）的。你需要的行是 version 最高的那一条，而不是 created_at 最新的那一条。"

3. 利用文件系统 & 渐进式披露

Skill 是文件夹，不是单个文件。将详细参考文档拆分到 references/api.md，模板放到 assets/，Claude 按需读取，而非一次性加载全部内容。这利用了 Agent 的工具调用能力实现"渐进式信息披露"。

4. 为模型写描述，不为人写

Skill 的 description 字段是 Claude 用来判断"有没有匹配的 Skill"的——它的作用是描述何时触发这个 Skill，而非概括内容。

❌ 为人写的描述✅ 为模型写的描述
"帮助部署服务""当用户要求部署、推送或发布 <service> 到 <env> 时使用此 Skill"
"代码质量检查工具""当用户要求审查 PR、检查代码风格或在合并前审计代码时触发"

5. 帮助 Claude 记住状态

在 Skill 内部存储数据（日志文件、JSON、SQLite）。例如，standup-post Skill 维护一个 standups.log，让 Claude 知道自上次运行以来发生了什么变化，避免重复劳动。

6. 打包脚本而非让 Claude 重写

把可执行脚本放入 Skill（Python、Bash 等），让 Claude 将算力花在编排与组合上，而非重复构建样板代码。这大幅减少了 token 消耗和出错概率。

7. 按需 Hook：护栏而非枷锁

Anthropic 实现了两个创新的按需 Hook：

  • /careful — 阻断危险命令（rm -rf、DROP TABLE、kubectl delete）
  • /freeze — 阻止对指定目录之外的任何编辑

这两个 Hook 作为用户主动激活的安全开关，而非始终开启的限制，平衡了安全性与灵活性。

分发与度量

两种分发方式

  1. 仓库内检入：将 Skill 放入 ./.claude/skills，随项目代码版本控制
  2. 插件市场发布：通过插件系统分发给更广泛的用户群

内部策展流程

Skill 的生命周期遵循"有机生长"模式：

  • 开发者将 Skill 放在沙盒文件夹中试用
  • 获得团队认可后，自然扩散
  • 成熟后通过 PR 合并到正式市场

度量与数据驱动

Anthropic 使用 PreToolUse Hook 在公司范围内记录所有 Skill 的使用情况，识别：

  • 热门 Skill——被广泛采用，值得进一步优化
  • 触发不足的 Skill——描述可能不够精准，需要调整触发条件

核心启示

原文关键引述：

"Skills best practices are still evolving. Most of our best skills began as a few lines and a single gotcha, then got better because people kept adding to them as Claude hit new edge cases."

—— Skill 最佳实践仍在演进。我们最好的 Skill 大多始于几行文字和一个 Gotcha，然后因为人们不断在 Claude 遇到新边界情况时往里添加内容而变得更好。

五个关键结论

  1. Skill 的本质是组织知识——不是教 Claude 编程，而是教它你的团队、代码库和业务的独特上下文。
  2. 从最小化开始——最好的 Skill 不是一次性设计出来的，而是在使用中逐步演化成型的。几条指令 + 一个 Gotcha 就足以起步。
  3. 描述字段是 Skill 的"搜索引擎优化"——写描述时思考"Claude 看到用户的什么请求时应该触发这个 Skill？"
  4. 文件系统是天然的上下文管理工具——利用文件夹结构实现渐进式加载，避免一次性倾泻大量信息进入上下文窗口。
  5. 用数据驱动迭代——通过 Hook 记录使用数据，发现哪些 Skill 真正被用起来了，哪些需要调整描述或内容。
实践建议：如果你正在构建自己的 Skill，建议从第 2 类（产品验证）或第 8 类（Runbook）入手——这两类 ROI 最高，能最快看到 Claude 从"通用助手"变成"了解你系统的队友"。
