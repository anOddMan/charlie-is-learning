Anthropic 自助数据分析实践
—— 用 Claude 驱动企业级分析智能体

原文：How Anthropic enables self-service data analytics with Claude · 来源：claude.com/blog · 2026年6月

95%内部业务分析查询由 Claude 自动完成
~95%综合准确率（含对抗审查后）
21% → 95%+Skills 层带来的准确率飞跃
~99%特定领域可达到的准确率

一、概述与核心数据

Anthropic 数据团队发布了一篇深度案例研究，揭示了他们如何用 Claude 驱动的分析智能体实现企业级自助数据分析。 核心成果：将 95% 的内部业务分析查询自动化，综合准确率达到 ~95%， 从而将数据科学团队从大量临时取数请求中解放出来，专注于因果建模、预测、机器学习等高价值战略工作。

"分析准确率对于 LLM 来说本质上是一个上下文与验证问题，而不是代码生成问题。" —— Anthropic 数据团队

核心洞察：LLM 生成 SQL 的能力已经不是瓶颈 —— 真正的问题在于：

  • 如何将模糊的业务问题映射到正确的数据实体
  • 如何在模式持续变化的环境中保持映射关系最新
  • 如何验证智能体确实找到了正确的信息

三大关键失败模式

失败模式 问题描述 典型场景
概念↔实体歧义 智能体无法将业务概念映射到正确的数据字段（数百万候选中） "活跃用户"可能对应数十个不同定义和字段；需要确定什么行为算"活跃"、包含/排除标准、回溯窗口等
数据陈旧 模式、定义、数据源持续变化，智能体的知识在数周内就会过时 文档未及时更新导致智能体返回看似合理但实际错误的答案
检索失败 正确信息确实存在，但智能体在海量搜索空间中找不到 数据模型中有正确的字段注释，但智能体在查询时绕过了它

二、Agentic 分析栈（四层架构）

▲ 四层 Agentic 分析栈架构图（自下而上：基础 → 真相源 → Skills → 验证）

① 数据基础（Data Foundations）

实践具体措施
规范数据集 将概念收敛到单一受管控的表（如将 40 个"收入"候选表收敛为 1 个官方数据集）
强制标准 CI 检查、结构路由、强制规则防止治理退化
同位制品 所有数据代码（模型、语义层、参考文档、仪表盘）放在单一仓库中，具有跨层 CI 完整性检查
元数据即产品 列/表描述、粒度文档、血缘、所有权维护与数据转换同等级别的严谨性

② 真相源（Sources of Truth）

智能体查询数据仓库时参考的导航面（按信任度降序排列）：

  1. 语义层 — 编译后的指标/维度定义；若问题能清晰映射，智能体直接调用函数获取唯一规范数字
  2. 血缘与转换图 — 让智能体推理上游模型、弃用状态、粒度兼容性
  3. 查询语料库 — 历史 SQL（但原始检索仅贡献 <1% 准确率提升，蒸馏为结构化文档后才有效）
  4. 业务上下文 — 公司知识图谱（路线图、决策日志、组织架构）—— 最被低估的一层，解决环境引用歧义

三、Skills 层深度解析 ★ 最关键的突破

没有 Skills：准确率 ≤ 21%  |  有 Skills：准确率持续 > 95%，特定领域 ~99%

什么是 Skill？

在 Claude Code 中，一个 Skill = 一个 Markdown 文件夹，智能体按需读取。 Skill 编码的是程序性知识——应该查阅哪些数据源、按什么顺序、如何处理歧义、以及一个完成的分析应该长什么样。

成对 Skill 设计模式

Skill 类型职责结构
知识 Skill 领域数据导航：先尝试语义层 → 指向 ~30 个参考文件（表、列、JOIN、陷阱） 薄顶层路由器 + 大量参考文件，在写任何查询之前就缩小搜索空间
Unbook Skill 编码资深分析师的流程：澄清需求 → 找数据源 → 执行查询 → 对抗审查循环 捆绑可复用的分析模式（留存曲线、漏斗分析等）

写给 LLM 看的参考文档设计原则

  • 描述表的粒度、范围、排除项——不仅仅是列定义
  • 记录机制陷阱（如"排除免费邮箱域名但保留自定义域名"）
  • 显式路由触发器（如"IF 问题是关于实验提升… DO NOT 用于原始事件计数"）
  • 渐进式加载：先加载元数据（~50 tokens）→ SKILL.md（~500 tokens）→ 详细参考（~2000+ tokens），仅加载需要的

④ 验证层（Validation）

验证类型机制
离线评估 问题/答案对固定在快照日期上，存储为遥测数据（非测试日志），按领域控制发布门槛
消融测试 验证每个 Skill 组件实际贡献了多少准确率
在线监控 对抗审查子智能体 + 用户纠正采集为新的评估候选

四、关键反模式与教训

尝试的做法结果教训
向智能体提供数千条历史 SQL 作为检索上下文 准确率提升 <1% 更令人震惊的是：~80% 的错误答案中，智能体刚刚读取的文件里已经包含正确答案——它看见了但没使用。原始检索不是答案，结构化整理才是。
用 LLM 自动生成指标定义 净负价值 LLM 生成的定义把同样的歧义编码了进去——自动化的不是解决方案，而是问题本身。
添加对抗审查（adversarial review） +6% 准确率
+32% tokens
+72% 延迟		 有效但代价高，需要在准确率和成本/延迟之间权衡。

五、准确率漂移：Skills 的维护是工程问题

~95%有维护时的准确率
~65%一个月无维护后
~90%数据模型 PR 包含 Skill 变更

Anthropic 的解决方案：将 Skill 维护工程化——

  • Skill Markdown 文件与转换模型放在同一仓库
  • 代码审查 Hook：任何报表模型的变更如果没有触及 Skill 文件，自动标记
  • 结果：~90% 的数据模型 PR 在同一 diff 中包含了 Skill 变更
  • 跨界面一致性：同一个 Skill 同时服务 Slack 问答、IDE 查询、仪表盘、独立智能体——单一规范源自动同步

六、核心启示

  1. 准确率提升不靠更强模型，靠更好的上下文工程——从 21% 到 95% 的飞跃来自 Skills 架构，而非模型升级
  2. 结构化文档 > 原始检索——扔给智能体一堆 SQL 文件几乎没用；精心策划、为 LLM 检索优化的参考文档才是关键
  3. 程序性知识必须显式编码——不是"数据在哪里"，而是"遇到某类问题应该怎么处理"
  4. 维护是不可协商的——不维护的 Skills 在一个月内从 95% 退化到 65%。Skills 维护必须嵌入工程工作流
  5. 规范数据基础是前提——如果数据本身没有治理（40 张"收入"表），再好的 Skills 也无从下手
  6. 对抗审查有效但昂贵——+6% 准确率换 +32% tokens 和 +72% 延迟，需要按场景权衡
