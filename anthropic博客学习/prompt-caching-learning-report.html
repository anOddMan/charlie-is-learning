Prompt Caching 最佳实践学习报告

基于 Anthropic Claude Code 团队的工程经验总结

来源: Anthropic 官方博客
作者: Thariq Shihipar
发布日期: 2026年4月30日
阅读时长: 约5分钟

概述

在工程领域常言"缓存主宰一切"（Cache rules everything around me），对于 AI Agent 产品同样如此。

核心论点

长时间运行的 Agent 产品（如 Claude Code）之所以可行，完全依赖于 Prompt Caching 技术。它允许复用之前轮次的计算，显著降低延迟和成本。

关键洞察

Claude Code 团队将整个 harness 围绕 Prompt Caching 构建。高缓存命中率可降低成本并为订阅计划提供更宽松的速率限制。团队甚至会设置警报监控缓存命中率，命中率过低时触发 SEV（严重事件）。

Prompt 布局策略

Prompt Caching 通过 前缀匹配 工作——API 缓存从请求开头到每个 cache_control 断点的所有内容。这意味着内容的排列顺序至关重要。

核心原则

静态内容在前，动态内容在后。尽可能让多个请求共享相同的前缀。

Claude Code Prompt 结构层次
静态系统提示 + 工具定义（全局缓存）
↓
CLAUDE.md（项目级缓存）
↓
会话上下文（会话级缓存）
↓
对话消息（动态增长）
常见陷阱
  • 在静态系统提示中放置精确时间戳
  • 非确定性地随机排列工具定义顺序
  • 更新工具参数（如 Agent 工具可调用的 agent 列表）

消息更新机制

Prompt 中的信息可能过期（如时间、文件变更）。直觉上可能想更新 Prompt，但这会导致缓存失效，代价昂贵。

解决方案

通过消息传递更新信息，而非修改 Prompt。Claude Code 在下一个用户消息或工具结果中添加 <system-reminder> 标签，携带更新信息，从而保留缓存。

XML system-reminder 示例 
<system-reminder>
  当前时间: 2026-05-27 10:30:00
  文件状态: src/app.py 已被用户修改
</system-reminder>

模型切换陷阱

Prompt 缓存是模型专属的，这使缓存的成本计算变得反直觉。

反直觉示例

如果已与 Opus 进行 100k tokens 的对话，想问一个简单问题：切换到 Haiku 反而更昂贵，因为需要为 Haiku 重建整个 Prompt 缓存。

正确做法

如需切换模型，使用 子 Agent（Subagent）。让 Opus 准备"交接"消息给另一模型完成任务。Claude Code 的 Explore Agent 就采用这种方式（使用 Haiku）。

工具管理策略

会话中途更改工具集是最常见的缓存破坏方式。直觉上应该只给模型当前需要的工具，但工具是缓存前缀的一部分，添加/移除工具会使整个会话的缓存失效。

Plan Mode 设计案例

直觉方案：进入 Plan Mode 时，只保留只读工具 → 破坏缓存

正确方案：始终保留所有工具，将 EnterPlanMode 和 ExitPlanMode 作为工具本身。模型通过系统消息获知 Plan Mode 指令，工具定义永不改变。

附加收益

EnterPlanMode 作为工具，模型可自主进入规划模式检测复杂问题，无需任何缓存破坏。

defer_loading 延迟加载

Claude Code 可加载数十个 MCP 工具，每次请求全部包含代价高昂，但中途移除会破坏缓存。

解决方案：发送轻量级 stub（仅工具名 + defer_loading: true），模型通过 tool search"发现"时再加载完整 schema。stub 顺序固定，保持缓存前缀稳定。

压缩与缓存

当上下文窗口耗尽时，需要压缩对话历史并继续新会话。压缩与缓存的交互容易出错。

常见错误

发送完整对话让模型生成摘要时，使用独立 API 调用 + 不同系统提示 + 无工具。这导致前缀从首个 token 就不匹配，整个缓存失效。对话越长，这次调用越昂贵。

正确方案：Cache-Safe Forking
  • 使用与父会话完全相同的系统提示、用户上下文、系统上下文、工具定义
  • prepend 父会话消息，append 压缩提示作为新用户消息
  • API 视为几乎相同的请求 → 缓存前缀复用
  • 仅新增 token 是压缩提示本身
注意事项

需预留"压缩缓冲区"，确保上下文窗口有足够空间容纳压缩消息和摘要输出 token。

好消息

Anthropic 已将这些经验整合到 API 的 compaction 功能中，可直接应用这些模式。

核心要点总结

原则 说明 错误做法 正确做法
前缀匹配 前缀任意位置的变化使后续全部失效 随机排列内容顺序 静态在前，动态在后
消息优先 用消息传递更新而非修改 Prompt 编辑系统提示更新时间/状态 使用 system-reminder 标签
稳定工具集 工具定义属于缓存前缀 中途添加/移除工具 工具作为状态切换器，defer_loading
避免模型切换 缓存是模型专属 会话中直接切换模型 使用子 Agent 交接
监控命中率 缓存失效严重影响成本和延迟 忽略缓存指标 设置警报，视失效为事故
Fork 共享前缀 侧计算需复用父会话前缀 使用不同系统提示压缩 相同参数 + append 提示消息

实践建议

构建 Agent 时的检查清单
  • 系统提示是否完全静态？时间戳等动态信息应通过消息传递
  • 工具定义顺序是否固定？是否避免非确定性排序
  • 工具参数是否稳定？Agent 列表等应通过其他方式管理
  • 状态切换（如 Plan Mode）是否通过工具而非工具集变更实现
  • 压缩/摘要等侧计算是否使用与主会话相同的前缀参数
  • 是否设置了缓存命中率监控和警报
关键心态

Claude Code 从第一天起就围绕 Prompt Caching 构建。构建 Agent 产品时，建议从一开始就将缓存作为核心约束纳入设计，而非事后优化。
