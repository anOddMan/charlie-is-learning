什么是 Loops？

Loops（循环） 是 Claude Code 团队在 2026 年 6 月 30 日 正式提出的核心概念。它指的是：

"Agents repeating cycles of work until a stop condition is met."
— 智能体以循环方式重复工作，直到满足停止条件。

这篇博客由 Claude Code 团队的 Delba de Oliveira 和 Michael Segner 撰写，系统性地阐述了 如何从"手动向 AI 发指令"跃迁到"设计自动循环系统"。

核心思想 — 从手动到自动

博客引用了几位关键人物的核心观点：

"You shouldn't be prompting coding agents anymore. You should be designing loops that prompt your agents."

— Boris Cherny（Claude Code 创始人）& Peter Steinberger（OpenAI）

"The romantic version of a loop is 'you write loops, a thousand agents build your company overnight.'

"The production version is 'you write loops, then most of your job is making sure they stop.'"

这段精辟的对比揭示了一个现实：循环系统的难点不在于"让 AI 干活"，而在于精确地定义停止条件和失败边界。

1. Turn-Based Loop — 默认对话循环

工作原理

每次你向 Claude Code 发 Prompt，就启动了一个 Turn-Based Loop。Claude 会：

  1. 收集上下文（读取文件、查看 Git 状态）
  2. 执行操作（写代码、运行命令）
  3. 自我检查（测试是否通过、构建是否成功）
  4. 如需要，重复上述步骤
  5. 回复用户

关键特征

属性说明
触发方式用户每次发送 Prompt
停止条件Claude 判定任务完成，或需要更多上下文
适用场景单次任务、非周期性工作
Token 管控写具体明确的 Prompt；用 Skills 强化验证能力

优化技巧

SKILL.md将手动验证编码为 Skills
# 把"我每次手动做的检查"写成 SKILL.md
# Claude 会据此自动完成端到端的自我验证

## 示例：编码代码质量标准
检查清单:
1. `npm run build` 通过
2. `npm test` 全部通过
3. 没有 console.log 残留
4. TypeScript 类型检查零错误
5. 新增代码有对应的测试覆盖
核心教训：用可量化的检查（测试通过、构建成功、0 错误）替代主观判断，让 Claude 能自动化自我验证。模糊的"做好一点"远不如"测试全部通过"有效。

2. /goal — 目标驱动循环

工作原理

/goal 延长 Claude 的迭代轮数，持续工作直到验证条件满足或达到轮数上限。 其关键是 Evaluator 模型（默认 Haiku，一个小而快的模型）——它独立于执行模型，每轮检查条件是否满足，避免自我评估偏差。

命令用法

BASH/goal 命令示例
# 基本用法：设定可验证目标
/goal get the homepage Lighthouse score to 90 or above, stop after 5 tries

# 非交互模式（headless 执行）
claude -p "/goal CHANGELOG.md has an entry for every PR merged this week"

# 恢复会话中的活跃目标
claude --resume          # 活跃的 /goal 会自动恢复
claude --continue

# 查看当前目标状态和 Token 用量
/goal                        # 裸命令 → 显示状态 + 使用量

# 清除当前目标
/goal clear

编写有效条件的技巧

原则好例子差例子
可测量的终点"All tests in test/auth pass""Make the auth better"
明确的检查机制"npm test -- --coverage exceeds 80%""The code looks good"
相关约束"No ESLint errors, stop after 5 retries""Fix everything"
关键洞察：条件必须写成 Claude 自己输出就能证明的东西。例如 "All tests pass" 有效，因为 Claude 执行 npm test 后结果就在当前 transcript 中。Evaluator 模型默认使用 Haiku（小、快、便宜），与大模型分工——"干活的模型"和"检查的模型"不是同一个，消除自我评价偏差。
技术限制：同一时间只有一个活跃的 /goal；条件最长 4,000 字符；Evaluator 每次返回简短理由说明条件为何满足/不满足；版本要求 v2.1.139+。

3. /loop — 定时循环

工作原理

/loop 本质上是 cron + prompt：按指定时间间隔重复执行 Prompt。所有"智能"都由你的 Prompt 提供——何时停止、如何处理错误、如何判断完成。

两种模式

模式语法行为适用
固定间隔 /loop 5m check the deploy 转为 Cron 表达式，按固定频率执行
单位：s / m / h / d，最少 1 分钟
7 天后自动过期		 CI 轮询、部署监控、定期检查
动态间隔（自调节） /loop check whether CI passed Claude 根据当前情况自己选择间隔（1 分钟 ~ 1 小时）
每次迭代打印选择理由		 状态未知的任务、需要"聪明等待"的场景

命令示例

BASH/loop 命令示例
# 固定间隔：每 5 分钟检查一次部署状态
/loop 5m check the deploy

# 动态间隔：Babysit 所有 PR（Boris Cherny 的真实案例）
/loop babysit all my PRs. Auto-fix build issues,
       and when comments come in, use a worktree agent to fix them.

# 检查 CI 状态（自定义间隔）
/loop check whether CI passed

# 停止循环
# 按 Esc 键 —— 在下一次迭代前
重要限制：/loop 在你的本地电脑上运行。电脑关机，循环就停止了。 需要跨重启持久化，使用桌面定时任务或云端 Routines（/schedule）。

架构解析

/loop 的核心实现非常简约：loop.ts 解析器将时间间隔转为 Cron 表达式 → 创建定时任务 → 立即执行第一次迭代。 这意味着 基础设施部分极薄——所有"智能"（停止判断、错误处理、任务分派）都在 Prompt 层面实现， 你不需要写 YAML 配置、DAG 定义或工作流 DSL。

4. Proactive Loops — 主动循环（无人值守）

工作原理

Proactive Loops 是最高级形态：在没有人实时参与的情况下，由事件或计划触发，自动完成完整工作流。 它由前面的原语组合而成，再加上几个关键能力：

组件作用
Auto Mode去掉每次工具调用的确认弹窗——Claude 在单轮内自动批准所有工具调用
Dynamic Workflows（研究预览）Claude 编写 JS 编排脚本，并行派发最多 1,000 个子 Agent（16 个并发），内置对抗性验证
/schedule云端持久化的定时 Routine——不依赖本地电脑，跨重启运行

组合示例

BASHProactive Loop 组合案例
# 一个完整的 Bug Triage 自动化循环
/schedule every hour: \
  check #project-feedback for bug reports. \
  /goal: don't stop until every report found this run \
  is triaged, actioned, and responded to. \
  When fixing a bug, use a workflow to explore three \
  solutions in parallel worktrees and have a judge \
  adversarially review them.

这个例子展示了三个层次的能力叠加：

  1. /schedule every hour：云端定时触发
  2. /goal + 停止条件：每个 bug 报告必须被分类、处理、回复才算完成
  3. Dynamic Workflow：三个并行解决方案 + 对抗性评审（Judge 模型）

决策指南：何时用哪个

任务类型推荐原语理由
简单单次修改直接 Prompt不需要循环的开销
有明确可验证目标的复杂任务/goal自动迭代到目标，Evaluator 保证质量
持续监控 / 轮询外部状态/loop定时触发，外部系统状态变化时响应
大规模代码迁移 / 批处理Dynamic Workflows并行 + 对抗验证，处理大量独立任务
周期性重复任务/schedule 或系统定时任务持久化执行，不依赖本地电脑
关键决策原则：任务越小、越确定，就越不应该用重循环。简单任务用复杂循环，是纯 Token 浪费。 相反，复杂且有明确验证条件的任务，不用循环而手动轮番 Prompt，是纯人力浪费。

代码质量保障

当 AI 大量生成代码时，质量保障变得关键。博客提出了四条原则：

1. 保持代码库整洁

Claude 会遵循项目中已有的模式和规范。良好的代码基础 → 良好的 AI 输出。

2. 给 Claude 自我验证的能力

用 Skills（SKILL.md） 编码质量标准——不是写给别人看的，是写给 Claude 读的验证清单。

3. 让文档易于获取

框架和库的最新最佳实践文档应该放在 Claude 能访问到的地方（项目中的 docs/ 或 CLAUDE.md 引用）。

4. 使用第二个 Agent 做代码审查

一个全新上下文的 Reviewer 偏见更少。使用 /code-review skill 或 GitHub Code Review。

"When an individual result doesn't meet the standard, don't stop at fixing the issue — encode the lesson to improve the system for all future iterations."
— 某个结果不达标时，不要止步于修复问题——把教训编码进系统，改进所有未来的迭代。

Token 成本管理 — 最关键的工程问题

成本残酷现实

场景Token 放大倍数说明
普通聊天1×（基准）单次 Q&A
单 Agent 循环~4×多次工具调用 + 自我验证
多 Agent 协作~15×Opus + Sonnet 协作可提升 90%+ 性能
真实翻车案例：Uber 在 4 个月内烧完了全年 AI 预算，随后对每个员工设置了 $1,500/月 的 AI 工具费用上限 （包括 Claude Code 和 Cursor）——来源：TechCrunch / Bloomberg，2026 年 6 月。

六个成本管理策略

#策略具体做法
1选对原语和模型小任务不需要多 Agent 或循环；简单分类用 Haiku 而非 Opus
2定义明确的成功/停止条件具体的"done"定义让 Claude 更快到达终点，减少无效迭代
3大规模前先小范围试点先在 10 个任务上测用量，再推 1,000 个
4确定性工作用脚本运行脚本的成本远低于让模型推理每一步
5间隔匹配实际变化频率不要比事件发生频率更频繁地运行 Routine
6监控用量/usage（按 skills/subagents/MCP 拆分）、/goal 裸命令（显示 turns/tokens）、/workflows（按 Agent 的 Token 用量）

成本路由策略

STRATEGY按任务类型分配模型
# 不同任务 → 不同模型 → 不同成本
路由/分类/摘要    → Haiku  ($1.00/1M in)     # 便宜
标准编码/RAG      → Sonnet ($3.00/1M in)    # 适中
复杂推理/架构决策  → Opus   ($15.00/1M in)   # 最贵——少用
Evaluator（验证）  → Haiku  (默认)           # 检查模型应与执行模型分离

三道硬停机制 — 生产环境必备

博客特别强调了三个生产环境必备的熔断机制：

熔断机制触发条件环境变量示例
无进展熔断 3 轮无文件改动 → 判定为"熔毁" CB_NO_PROGRESS_THRESHOLD=3
重复错误熔断 同一错误出现 5 次 CB_SAME_ERROR_THRESHOLD=5
用量预算上限 每小时调用数 / Token 数达上限 MAX_CALLS_PER_HOUR、MAX_TOKENS_PER_HOUR
不做硬停 = 财务风险。没有预算上限的循环系统就像没有刹车的高速列车。Uber 的例子就是最直接的警示。

从 Prompt 到 Loop — 三步转换法

步骤从到
1. 可验证的停止条件 "把这个功能做好" "npm run build 通过 + 所有页面正常渲染"
2. 状态追踪 无状态，Claude 靠记忆 维护 PROGRESS.md：当前阶段 + 已完成项 + 遇到的问题
3. 反馈循环 做完就结束 每个模块后 → 构建/测试 → 修复错误 → 继续下一个模块；同一问题最多重试 5 次
