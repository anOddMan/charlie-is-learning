🔧 A Harness for Every Task: Dynamic Workflows in Claude Code

原文作者：Thariq Shihipar & Sid Bidasaria（Anthropic 技术团队）
发布日期：2026-06-02  |  报告生成：2026-07-01

1. 概述与背景

2026年6月2日，Anthropic 发布了一篇里程碑式的博客文章，正式介绍了 Claude Code 动态工作流（Dynamic Workflows）——这是 Claude Code 迄今最重要的能力升级。核心思想是：Claude 不再依赖单一的默认上下文窗口，而是在每次任务中动态"编写"一套专属的编排层（Harness），通过 JavaScript 脚本生成并协调多个子代理（sub-agent），每个子代理拥有独立的上下文窗口和 git worktree 隔离环境。

核心理念：将编排逻辑从上下文窗口转移到代码中。Claude 不再在脑子里"想"该怎么分工，而是"写"一段 JavaScript 程序来精确控制分工、并行、验证和资源消耗。

1.1 解决了什么问题

传统单代理（single-agent）模式在复杂任务中会遭遇瓶颈：随着任务规模增长，上下文窗口被大量中间结果污染，模型出现"注意力稀释"。动态工作流通过结构化分解 + 独立上下文 + 代码级编排解决了这个问题。

1.2 三大失败模式

失败模式描述动态工作流的应对
Agentic Laziness
代理惰性		 模型在长会话中倾向于抄近路、跳过步骤、敷衍了事 每个子代理只负责一个明确的小任务，独立上下文减少认知负担，code 级编排强制执行完整流程
Self-Preferential Bias
自我偏好偏差		 模型"信任自己生成的输出"，自己写的代码自己检查不出问题 Adversarial Verification 模式：验证者是一个独立代理，从未见过生产者上下文，结构性地消除盲点
Goal Drift
目标漂移		 长时间运行后模型逐渐偏离原始目标，产出与需求不对齐 前期问题分解层明确目标边界，合成阶段强制执行面向目标的输出校验

2. 架构设计

2.1 Harness 机制 — 从"思考"到"编程"

动态工作流的核心创新在于：编排不是 prompt engineering，而是真正的编程。Claude 生成一个 JavaScript 文件，该文件在一个沙盒化运行时中执行，通过注入的 DSL 原语来生成和协调子代理。

ultracode 的本质：它不是一个新的 API effort level，而是 xhigh effort + 会话中系统消息注入的组合。这给了编排者（Orchestrator）足够的推理深度来做规划，同时赋予了启动工作代理的"常设权限"。

2.2 JavaScript Harness API 接口

脚本在一个受限的沙盒 JS 环境中运行，以下全局函数被注入（无需 import）：

API签名功能
agent() agent(prompt, opts?) → Promise 生成一个子代理，返回其结果。支持 schema（结构化输出校验）、model、provider、agentType、isolation: 'worktree'、label、phase
parallel() parallel(thunks[]) → Promise 并行执行一组函数，等待全部完成（显式 barrier）
pipeline() pipeline(items, ...stages) → Promise 每个 item 依次通过所有 stage 处理，stage 间无 barrier
workflow() workflow(nameOrRef, args?) → Promise 调用已保存的工作流（仅支持一层嵌套）
phase() phase(name) 在进度视图中标记一个阶段标签
log() log(...args) 向用户输出进度信息
budget { total, spent(), remaining() } 共享 token 池，耗尽时 agent() 抛出异常（硬上限）
args 全局变量 调用工作流时传入的结构化参数，使保存的工作流可参数化

代码示例 — 对抗性审查工作流：

JavaScriptadversarial-review.js
export const meta = { name: "adversarial-review", description: "find bugs, cross-examine them" }

phase("Find")
const findings = await parallel(
  ["correctness", "security", "performance"].map(lens => () =>
    agent(`Review the diff through the ${lens} lens. List concrete issues.`, { schema: FINDINGS })),
)

phase("Verify")
return await pipeline(
  findings.filter(Boolean).flatMap(f => f.issues),
  issue => agent(`Try to refute: ${issue.desc}`, { provider: "claude-code", schema: VERDICT }),
)

2.3 运行时约束

约束项值说明
并发上限min(16, cores−2)同时运行的代理数不超过此值
总代理上限1,000 / 次运行防止失控的资源消耗
嵌套层级仅 1 层 workflow() 嵌套防止无限递归
沙盒限制无 fs / shell / Node API仅注入 DSL + 标准 JS（JSON, Math, Array）
确定性Date.now() / Math.random() 抛出异常确保日志可回放恢复
用户交互不支持中途输入仅权限弹窗可暂停；分阶段签核需拆分为多个工作流
子代理模式acceptEdits子代理自动接受编辑，无需逐次确认

2.4 触发方式

  • 在 prompt 中包含关键词 ultracode
  • 设置 /effort ultracode 使整个会话自动启用工作流编排
  • 运行内置工作流如 /deep-research
  • 从 ~/.claude/workflows/ 加载并运行保存的工作流（按 s 键保存）

3. 六大编排模式

🔀 3.1 Classify-and-Act

分类 → 路由：一个分类代理判断任务类型，然后路由到对应的专家代理。适合有明确边界和分类标准的场景（如 issue 分诊、按复杂度路由）。

分类路由

⚡ 3.2 Fan-out-and-Synthesize

拆分 → 并行 → 合并：将大任务拆成 N 个独立子任务并行处理，最后合成结果。总耗时 ≈ 最慢子任务。适合大规模迁移、代码库审计。

并行合并

🛡️ 3.3 Adversarial Verification

独立验证者挑战每个输出：对每个生成结果，运行一个独立代理尝试在特定维度上"驳倒"它。只有足够多验证者无法驳倒的声明才被接受。这是消除自我偏好偏差的核心机制。

安全验证

💡 3.4 Generate-and-Filter

生成 → 评分 → 筛选：生成多个候选方案，按评分标准筛选，去重，返回验证过的结果。适合创意类/探索性任务。

创意筛选

🏆 3.5 Tournament

多代理竞争 → 两两评判 → 优选：多个代理执行同一任务（不同策略），通过两两比较选出最佳方案。适合需要相对判断的 Best-of-N 场景。

竞争评判

🔄 3.6 Loop-Until-Done

迭代直到收敛：循环生成代理直到停止条件满足——如"连续两轮无新发现"、"无新错误"。适合 bug 清扫、内存泄漏审计等探索性任务。

迭代收敛

4. 实际案例

4.1 Bun 的 Zig → Rust 移植（Jarred Sumner）

一个被多次引用的外部案例：使用 fan-out 模式将大规模代码移植任务拆分到多个并行工作代理中。如果这种规模的重写可行，那么常规的依赖升级、API 迁移完全在射程之内。

4.2 Flutter Material 2 → Material 3 迁移（Very Good Ventures）

典型模式：fan-out-and-synthesize + adversarial verification + git worktree 隔离

  • 每个受影响的 package 获得独立的 git worktree
  • 迁移代理执行代码变更
  • 对抗性审查代理以 Material 3 兼容性标准检查每个修复
  • CI 门禁在合并后运行——与人类 PR 相同的质量关卡

4.3 Bug 清扫（Bug Sweep）

模式：fan-out + loop-until-done + analyzer 验证

  • 按组件 fan-out：每个组件一个子代理，独立上下文避免交叉污染
  • 每个子代理在多个维度上检查（正确性 / 安全 / 性能）
  • Loop-until-done：修复后重新扫描直到 analyzer 干净

4.4 深度研究（Deep Research）

fan-out 到多个信息源并行检索，adversarial verification 交叉验证事实声明，loop-until-done 持续搜索直到无新发现。这也是 /deep-research 内置命令的底层机制。

4.5 更多场景

  • 简历筛选：classify-and-act 按岗位分类，fan-out 并行评估，tournament 选出最优
  • 商业计划分析：每个代理从不同角度（市场/财务/技术/风险）评估
  • 规则挖掘：从会话历史中提取隐含规则模式
  • Evals 评估：fan-out 并行运行测试用例 + adversarial verification

5. 最佳实践与注意事项

5.1 何时使用动态工作流

✅ 适合：大规模迁移/重构、深度研究、多维度代码审查、bug 清扫、"宽"而非"深"的任务——需要并行 + 逐单元独立判断的场景。

5.2 何时不使用

❌ 不适合：动态工作流消耗的 token 是单次对话的数十倍。对于简单的日常编码任务（修一个 typo、加一个简单函数），使用动态工作流是杀鸡用牛刀，得不偿失。

5.3 关键技巧

  • 设置 Token 预算：使用 "use 10k tokens" 显式设置上限，防止失控
  • 保存可复用工作流：在工作流菜单按 s 保存，之后通过 ~/.claude/workflows/ 或 SKILL.md 引用共享
  • 分阶段签核：一个工作流 = 一个阶段，跨阶段决策需人工确认时拆分为多个工作流
  • 模型路由：编排者用 Opus（推理深度），执行者用 Sonnet（成本效率），在 agent() 的 model 参数中指定
  • 结构化输出：使用 schema 参数确保子代理返回可机器处理的结构化数据

8. 核心启示与思考

编排是新战场

动态工作流标志着 AI 编程工具从"更好的模型"竞争转向"更好的编排"竞争。单代理能力已接近天花板，下一个数量级的提升来自多代理协作。这本质上是对 LangChain、CrewAI 等传统 Agent 框架的"压缩"——当基础模型足够强大时，它可以直接生成编排代码，而不需要用户手写复杂的代理图。

关键洞察

  1. 代码优于 Prompt：编排逻辑用 JavaScript 表达比用自然语言 prompt 更精确、更可复用、更可调试。
  2. 结构消除偏见：Adversarial Verification 不是"让 AI 更努力检查"，而是通过架构设计（独立代理 + 隔离上下文）结构性消除自我偏好。
  3. 宽优于深：动态工作流的核心优势在于并行宽度，而非单个代理的深度。适合天然可并行的任务。
  4. Token 换质量：数十倍的 token 消耗换取结构性的质量保证。这是一个值得的权衡——但仅在任务复杂度匹配时。
  5. 可组合性：六大模式不是孤立的，可以组合使用——例如 fan-out 做广度、adversarial 做深度、loop-until-done 做收敛。

对实际开发的启示

  • 任务拆解能力成为关键技能：能否把一个复杂需求拆成可并行、可独立验证的子任务，决定了能多好地利用动态工作流。
  • 保存和共享工作流：好的工作流应该被保存、版本化、团队共享——这将成为团队知识资产的一部分。
  • 混合模型策略：编排用 Opus（推理深度），执行用 Sonnet（成本效率），这是成本最优解。
  • 与现有流程集成：工作流可以对接 CI/CD，使用与人类 PR 相同的质量门禁。
