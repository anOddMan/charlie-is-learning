为每个任务定制执行框架：Claude Code 动态工作流

来源：Anthropic 官方博客  |  作者：Thariq Shihipar & Sid Bidasaria  |  发布：2026-06-02  |  报告生成：2026-06-05

一句话总结：Claude Code 的动态工作流让 AI 自行编写并编排多 Agent 执行框架——针对每个任务动态生成定制化的 JS 脚本，调度多个子 Agent 并行或流水线协作，突破单上下文窗口的限制。

为什么需要动态工作流

单上下文窗口模式在大多数编码任务中表现良好，但在面对复杂任务时会暴露三种失效模式：

失效模式表现根因
1. Agent 懒惰 完成部分进度后自行停止，声称"已完成" 模型倾向于"够好就行"而非彻底完成
2. 自我偏好偏见 被要求验证自身结果时，倾向于认可自己的输出 同一上下文中的模型缺乏真正独立的审查视角
3. 目标漂移 经过多轮交互后逐渐偏离原始目标 长对话中上下文衰减和信息过载
核心洞察：这三种失效的共性根源是同一个上下文窗口承载了过多职责——既要理解任务、又要执行、还要自我审查。动态工作流通过职责分离来解决：让不同 Agent 各司其职，每个只关注自己的子任务。

架构：动态生成的 JS 执行框架

Claude 不是被固定配置驱动，而是动态编写一个 JavaScript 文件，该文件负责生成和协调多个子 Agent。每个子 Agent 拥有独立的上下文窗口、可选的独立模型和隔离的 Git worktree。

三大核心 API

agent(prompt, options) — 单个子 Agent

agent({ prompt: "分析这个文件", model: "sonnet", tokenBudget: "20k" })

创建一个子 Agent，拥有独立上下文窗口、可指定模型（Haiku/Sonnet/Opus）、Token 预算，可选独立 worktree 隔离文件变更。

parallel(tasks) — 并行扇出

parallel([taskA, taskB, taskC])

同时启动多个子 Agent，互不依赖。全部完成后聚合结果。适用于审查、搜索、多视角分析等可独立拆分的任务。

pipeline(stages) — 流水线串联

pipeline([stage1, stage2, stage3])

按顺序执行阶段，每个阶段的输出流入下一阶段。适用于生成→审查→修订等有依赖关系的多步骤流程。

六大工作流模式

这些模式可自由组合，形成复杂的工作流编排：

1. 分类-执行 Classify-and-Act

先用一个廉价的分类 Agent 判断任务类型，再路由到对应专业的执行 Agent。

2. 扇出-综合 Fan-out-and-Synthesize

将大任务拆分为互不依赖的子任务，并行分配给多个 Agent，最后汇总综合结果。这是最常用的模式。

3. 对抗验证 Adversarial Verification

一个 Agent 产出后，由另一个独立 Agent 专门找漏洞、挑错。两个 Agent 互相不了解对方的推理过程，实现了真正的独立审查——直接对抗自我偏好偏见。

4. 生成-过滤 Generate-and-Filter

先用多个 Agent 做头脑风暴自由生成，再用评分 Agent 按标准筛选。适合创意发散场景（命名、设计方向、架构方案）。

5. 锦标赛 Tournament

多个 Agent 两两竞争，优胜者晋级下一轮，直到选出最佳方案。适合需要多轮比较的决策场景。

6. 循环至完成 Loop Until Done

Agent 反复迭代直到满足停止条件。配合 /loop 命令实现持续执行，适合大规模迁移、持续监控等需要反复推进的任务。

何时不应该用动态工作流

重要警告：动态工作流的 Token 消耗显著高于单 Agent 模式。每个子 Agent 都有自己的上下文窗口，多 Agent 之间的协调也需要额外 Token。对于常规编码任务（单个 Bug 修复、简单功能添加），动态工作流是杀鸡用牛刀。
✅ 适合动态工作流❌ 适合单 Agent
需要独立审查视角的任务单文件小修改
跨越多个文件/模块的大范围改动简单功能添加
需要并行处理的批量任务代码片段解释
多步骤有依赖关系的复杂流程配置调整
需要多轮迭代直到满足条件的任务回答技术问题

实操建议

建议说明示例
详细 Prompt 给子 Agent 的 prompt 越具体越好——它们无法看到你与主 Agent 的对话历史 不只是 "检查代码"，而是 "检查 auth.js 中 JWT 过期逻辑的边界情况"
配合 /goal 和 /loop 用 /goal 定义长期目标，/loop 驱动迭代执行 /goal 将整个项目迁移到 TypeScript，然后让 Agent 循环推进
设置 Token 预算 为子 Agent 限定 Token 上限，避免成本失控 "用 10k token 分析这个模块"
保存工作流 用 s 命令保存有效的工作流，下次复用 保存到 ~/.claude/workflows 目录
共享为 Skill 将成熟的工作流封装为 Skill，团队内分发 migrate-ts.skill — 让任何成员直接运行团队验证过的迁移流程
模型路由的经济学：动态工作流的一大价值在于智能模型选择——分类/预处理用廉价的 Haiku，核心分析用 Sonnet，需要极高压准确度的验证环节才用 Opus。一个设计良好的工作流可将总成本控制在纯 Opus 方案的 20-30%。

核心启示

与 Skills 文章的内在联系：

动态工作流是 Skills 系统的自然延伸——Skills 解决了"教 Claude 知道什么"，动态工作流解决了"教 Claude 怎么做"。两者结合形成完整的能力栈：Skills 提供领域知识，工作流提供执行编排。

五个关键结论

  1. 上下文隔离是解决偏见的关键——让一个 Agent 独立审查另一个 Agent 的输出，是对抗"自我偏好偏见"最有效的手段。这本质上是一种结构化的同行评审。
  2. 按需消费模型——不是所有任务都需要 Opus。动态工作流的核心价值之一就是让 Haiku 处理简单环节，Opus 只用于关键判断。这既是成本优化，也是性能优化。
  3. 工作流是可以积累的资产——一次调试出的工作流可以保存、复用、共享为 Skill。团队的工作流积累就是组织的 AI 执行能力护城河。
  4. 动态 > 静态编排——传统的固定流水线（CI/CD pipeline）无法适应多变任务；让 AI 根据任务特征自行设计执行框架，是更灵活的方式。
  5. 别滥用——对于 90% 的日常编码任务，简单的单 Agent 模式仍然是最优解。动态工作流是为那 10% 的复杂任务准备的"重武器"。
