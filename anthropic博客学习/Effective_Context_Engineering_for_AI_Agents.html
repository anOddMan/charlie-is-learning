一、概述

本文是 Anthropic Applied AI 团队关于 Context Engineering（上下文工程） 的系统性论述。核心观点是：构建 LLM 应用正在从"写好提示词"转向"管理好上下文"——即回答一个更根本的问题："什么样的上下文配置最有可能让模型产生我们想要的行为？"

核心定义：上下文工程是指在大模型推理过程中，策划和维护最优 token 集合的策略体系，涵盖系统提示词、工具定义、Model Context Protocol (MCP)、外部数据、消息历史等全部信息。

随着 Agent 越来越多地在多轮推理和长时间跨度下运行，上下文工程正在成为构建可靠、可控 Agent 的关键能力。

二、上下文工程 vs 提示工程

维度 提示工程（Prompt Engineering） 上下文工程（Context Engineering）
焦点 写好"提示词" 管理"全部上下文状态"
范围 系统提示词的写作技巧 系统提示 + 工具 + MCP + 历史 + 检索数据
适用场景 单次分类、文本生成 多轮 Agent、长时间任务
工作方式 一次性编写 每轮推理前循环策划、迭代优化
挑战 措辞与格式 信息筛选、注意力预算分配、上下文污染

简而言之：提示工程是上下文工程的一个子集。在 Agent 场景中，Agent 在循环中运行，持续产生新的数据，上下文工程的任务就是从这个不断演化的信息宇宙中，筛选出能放入有限上下文窗口的高质量信息。

三、为什么上下文工程对构建 Agent 至关重要

注意力预算是有限资源

LLM 基于 Transformer 架构，每个 token 需要与其他所有 token 进行交互（n² 对关系）。上下文越长，模型捕捉这些两两关系的能力被稀释，形成 上下文衰退（Context Rot） 现象：随着 token 数增加，模型准确回忆信息的精度下降。

架构瓶颈

Transformer 的注意力复杂度为 O(n²)，长序列下位置编码插值等技术虽能缓解限制，但仍存在精度损失。

训练分布偏差

模型在训练中更多见到短序列，对长距离依赖的参数和经验都不足，长上下文的处理能力存在"性能梯度"而非硬性瓶颈。

关键洞察：上下文是"边际收益递减"的资源。每个新引入的 token 都会消耗注意力预算，因此必须精心策划哪些 token 进入窗口。

四、高效上下文的构成

上下文工程的指导原则：找到最小的、高信号的 token 集合，最大化期望结果的概率。

4.1 系统提示词

❌ 常见失败模式
  • 硬编码复杂的 if-else 逻辑到提示词中
  • 提供模糊、笼统的高层指导
  • 错误假设模型"知道"某些共享上下文
✅ 建议做法
  • 使用简单直接的语言
  • 找到"金发女孩区"——具体到引导行为，又灵活到允许模型自主判断
  • 先用最小提示在最好模型上测试，再根据失败模式增量完善

推荐的结构化方式：

<background_information>
  背景信息...
</background_information>

<instructions>
  核心指令...
</instructions>

## Tool guidance
工具使用指引...

## Output description
输出格式说明...
注意："最小" ≠ "简短"。仍需要提供足够的前置信息来约束行为。关键是从少到多，根据测试结果增量添加。

4.2 工具设计

工具定义了 Agent 与其信息/操作空间之间的契约。好的工具设计要点：

  • 自包含：功能单一、职责明确
  • 容错性强：能优雅处理错误
  • 意图清晰：工具名称和描述让 LLM 一目了然
  • 参数描述准确：参数名要符合模型的理解方式
  • 最小工具集：如果人类工程师都不能确定该用哪个工具，AI Agent 更做不到
  • 返回 token 高效：工具返回的信息要经过优化
常见陷阱：工具集过于臃肿，功能重叠，导致 Agent 在选择工具时产生歧义。维护一个最小的可用工具集对长交互中的上下文维护也至关重要。

4.3 示例与少样本（Few-shot）

继续保留少样本提示这一最佳实践，但要注意：

❌ 错误做法
  • 把所有边界情况塞进提示词
  • 试图列出每一条规则
✅ 正确做法
  • 精选一组多样化、典型的示例
  • 用示例来呈现期望行为模式

对 LLM 而言，好的示例胜过千言万语的规则描述。

五、上下文检索与智能搜索

Agent 的定义已趋同于：LLM 在循环中自主使用工具。模型越智能，Agent 的自主性就可以越高——能独立导航问题空间并从错误中恢复。

5.1 即时（Just-in-Time）上下文策略

与传统的"预处理所有相关数据"不同，即时策略让 Agent 维护轻量级标识符（文件路径、存储查询、Web 链接等），在运行时通过工具动态加载数据到上下文中。

Claude Code 的案例

Claude Code 使用这种做法进行复杂数据分析：模型编写针对性查询、存储结果、使用 head 和 tail 等 Bash 命令分析大量数据，而无需将完整数据对象加载到上下文中。

元数据的价值：文件系统结构本身就是重要信号。例如 test_utils.py 位于 tests/ 目录和 src/core_logic/ 目录暗示不同的用途。文件夹层级、命名规范、时间戳都是 Agent 理解和使用信息的线索。

5.2 渐进式信息发现

让 Agent 自主导航和检索数据，逐步发现相关上下文：

  • 文件大小暗示复杂度
  • 命名惯例提示用途
  • 时间戳作为相关性的代理指标
  • 每次交互的结果指导下一次决策

这种自我管理的上下文窗口让 Agent 只关注相关子集，而不是淹没在详尽但可能不相关的信息中。Agent 还可以通过笔记策略获得额外的持久化能力。

权衡：运行时探索比检索预计算数据慢，且需要精心的工程来确保 LLM 有正确的工具和启发式方法来有效导航信息空间。引导不当的话，Agent 可能浪费上下文在错误工具、死胡同或遗漏关键信息上。

六、长周期任务的上下文工程技术

长时间任务（从几十分钟到数小时的连续工作，如大型代码库迁移、综合研究项目）需要专门技术来突破上下文窗口的大小限制。

关键观点：等待更大的上下文窗口并不是根本解。在可预见的未来，任何大小的上下文窗口都面临上下文污染和信息相关性的问题。

Anthropic 提出了三种核心技术：

6.1 压缩（Compaction）

将接近上下文窗口限制的对话进行摘要压缩，然后用摘要初始化一个新的上下文窗口。这是处理长周期任务的第一杠杆。

Claude Code 的实现方式

将消息历史传给模型，让模型总结和压缩最关键的信息。模型保留架构决策、未解决的 bug 和实现细节，丢弃冗余的工具输出或消息。Agent 用压缩后的上下文加上最近访问的 5 个文件继续工作，用户获得无缝的连续性体验。

低挂果实——工具结果清理：一旦工具在历史深处被调用过，Agent 就不需要再看原始输出了。工具结果清理是最安全、最轻量的压缩形式。Anthropic 已在 Claude Developer Platform 上将此作为一项功能发布。

压缩的艺术在于取舍——过于激进的压缩可能丢失微妙但关键的上文信息。实现建议：

  • 先在复杂 Agent 轨迹上最大化召回率，确保压缩提示能捕捉每条相关信息
  • 再迭代提高精确率，消除多余内容

6.2 结构化笔记（Agentic Memory）

Agent 定期将笔记持久化到上下文窗口之外的内存中，在后续步骤中拉回上下文窗口使用。

Claude Code 的待办列表

Agent 维护 todo列表、NOTES.md 文件，跟踪跨复杂任务的进度。

Claude 玩 Pokémon

Agent 维护精确计数——"过去 1,234 步我一直在 Route 1 训练，皮卡丘升级了 8 级，还有 2 级达标"——开发地图、记录战斗策略。上下文重置后，Agent 读取自己的笔记继续数小时的训练序列。

Anthropic 已在 Claude Developer Platform 上发布了 Memory Tool（公开测试），通过文件系统让 Agent 更轻松地在窗口外存储和查询信息，支持跨会话构建知识库。

6.3 子 Agent 架构

不是让一个 Agent 维持整个项目的状态，而是让专门的子 Agent 处理聚焦任务，各自拥有干净的上下文窗口：

核心优势：关注点分离

  • 每个子 Agent 可以深入探索（甚至数万 token），但只返回精简的摘要（通常 1,000-2,000 token）
  • 详细的搜索上下文隔离在子 Agent 内部，主 Agent 专注于综合和分析结果
  • 这一模式在复杂研究任务上显著优于单 Agent 系统

6.4 三种技术对比

技术 适用场景 优势 注意点
压缩 需要大量来回对话的任务 保持对话的连续性 过度压缩可能丢失微妙上下文
结构化笔记 具有明确里程碑的迭代开发 持久化，开销极低 需 Agent 具备自律的笔记习惯
子 Agent 架构 复杂研究和分析，需要并行探索 关注点分离，上下文隔离 系统复杂度增加

七、核心原则总结

  1. 上下文是有限资源
    Transformer 注意力预算有限，每个 token 都要花得有价值。上下文长度增加带来的收益是边际递减的。
  2. 最小的、最高信号的 token 集合
    目标是找到能最大化期望结果概率的最小 token 集合。不是"尽量短"，而是"恰到好处"。
  3. 系统提示词要找到"金发女孩区"
    不要在提示词里硬编码脆弱逻辑，也不要只写模糊的高层指导。要足够具体以引导行为，又足够灵活以允许模型自主判断。
  4. 工具集要精简明确
    功能重叠的工具集是 Agent 失败的常见原因。维护最小可用工具集，确保每个工具意图清晰、自包含。
  5. 用精选示例代替穷举规则
    一套多样化、典型的示例比列出所有边界规则更有效。示例抵得上千言万语。
  6. 优先即时检索，而非预加载全部
    让 Agent 通过工具按需获取信息，模拟人类的"文件系统 + 书签"模式。元数据（目录结构、命名、时间戳）本身就是重要信号。
  7. 混合策略往往最佳
    静态信息预取 + 运行时按需检索的混合模式兼顾速度和灵活性。CLAUDE.md 预加载 + glob/grep 按需查询是典型案例。
  8. 压缩是第一杠杆
    当上下文窗口接近限制时，先尝试压缩。工具结果清理是最轻量、最安全的压缩方式。
  9. 笔记就是 Agent 的外部记忆
    结构化笔记提供了零开销的持久化能力。跨上下文重置后仍能保持连贯性，数小时任务也能协调执行。
  10. 子 Agent 实现关注点分离
    复杂任务中，主 Agent 保持高层策略，子 Agent 执行深耕。每个子 Agent 有干净的上下文窗口，返回精简摘要。
  11. 让智能模型智能地行动
    模型越强大，越不需要预设的工程。当前最佳建议仍然是："做最简单有效的事"。

八、总结与启示

一句话总结：上下文工程是从"写好提示词"到"管理好整个上下文生命周期"的范式转变。无论采用哪种具体技术，指导原则始终不变——用最小的 token 代价，获取最大的行为确定性。

对 Agent 开发者的行动建议

  • 从简单开始——用最少的上下文和最好的模型测试你的任务基线
  • 基于失败模式增量优化——不要一开始就试图覆盖所有边界
  • 工具设计投入在前——好的工具定义节省的远不止上下文空间
  • 压缩 + 笔记是基本功——至少实现这两个机制再考虑子 Agent
  • 持续审视上下文利用率——定期检查上下文窗口里有多少"信号"和多少"噪声"
  • 关注模型能力提升的节奏——模型越聪明，越少需要你事无巨细地铺路
